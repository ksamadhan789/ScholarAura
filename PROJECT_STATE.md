# PROJECT_STATE.md — ScholarAura

Compact project memory. Read this first at the start of every task. Keep it short; history goes in CHANGELOG.md, tasks in TODO.md.

## Project

- **Website name:** ScholarAura
- **Purpose:** E-learning + events + competitions + jobs + freelance platform for students and professionals, primarily in India. Single admin runs the platform; instructors post courses, recruiters post jobs, students/professionals post their own freelance listings.
- **Framework:** Next.js 14 (App Router), React, TypeScript, Tailwind CSS
- **Database:** PostgreSQL via Prisma (schema in `prisma/schema.prisma`, migrations in `prisma/migrations/`)
- **Authentication:** NextAuth — email/password plus Google sign-in. Roles: `STUDENT`, `INSTRUCTOR`, `ADMIN`, `RECRUITER`.
- **Payments:** Razorpay (one-time payments only, no subscriptions). Multi-currency display via an `ExchangeRate` table; charging in non-INR depends on the Razorpay account.
- **Hosting/deployment:** Vercel. CI on GitHub Actions ("Type check and test") runs on every PR.
- **Other services:** Resend (email), Bunny Stream (course videos — admin pastes a video ID, no upload through the app), Google Drive (stores resumes, course resource files, and generated certificates), Google Slides (certificate templates), Google Forms/Sheets (event attendance), Google Analytics, Sentry (error tracking), Cloudflare Turnstile (signup bot protection), OpenStreetMap Nominatim (free reverse geocoding for the location bar), Vercel Blob (temporary staging for large browser uploads — see "Files" decision below; requires `BLOB_READ_WRITE_TOKEN` in production).

Three gotchas worth remembering for any future image/canvas work: (1) create and revoke a `URL.createObjectURL()` blob URL within the *same* `useEffect` — splitting creation (e.g. into a `useState` initializer) from revocation (a separately-keyed effect) works in production but breaks under React 18 Strict Mode's dev-only mount→cleanup→remount cycle, since the cleanup fires and revokes the URL the `<img>` still points to; (2) Tailwind's Preflight sets `img { max-width: 100% }` globally, which clamps an image's rendered width to its container regardless of an explicit inline `width` — `max-width` isn't a specificity fight `width` can win, it always constrains the used width — so any image deliberately sized larger than its container (like this crop viewport) needs an explicit `max-width: none` override; (3) the pan-clamp math that keeps the image covering the viewport only makes sense once an axis actually overflows the viewport — applying the same min/max formula when an axis is smaller (letterboxed at low zoom) inverts the clamp bounds and snaps that axis to a corner the moment zoom or drag changes, so a letterboxed axis needs its own branch that just locks the offset to 0.

## Important Decisions

- **Payments:** every paid thing (course, event, competition, job boost) uses the same one-time Razorpay flow: create order → pay → verify signature → settle. A Razorpay webhook re-settles if the browser drops. Settlement is idempotent.
- **Job boosts** are their own product (`JobBoost` table + `featuredUntil` on Job) so a recruiter subscription tier can be added later without reshaping it.
- **Files** (resumes, course resources, student ID cards, competition entry files) live in Google Drive; only the Drive file ID is stored in the database. Every "upload a file instead of pasting a link" route shares one allow-list/size-cap/magic-bytes check from `lib/uploadValidation.ts` (images, PDF, Word, ZIP, 25MB). Most upload routes (profile photo, resume, job-application resume) still go straight through our own server as multipart `FormData`, capped well under Vercel's ~4.5MB request-body limit. The two that need to support genuinely large files — the student ID card (`/api/account/id-card`) and competition entry files (`/api/competitions/[slug]/submit`) — use **Vercel Blob's client-upload SDK** instead: the browser calls `upload()` from `@vercel/blob/client` to send bytes straight to Blob storage (a token-issuing route, `.../blob-upload/route.ts`, calls `handleUpload()` server-side after checking auth/eligibility), then the browser POSTs only the resulting `blobUrl` (plus `fileName`/`mimeType`) as small JSON to the existing confirm route, which downloads the bytes server-side (`lib/blobUpload.ts`'s `downloadBlobBytes()`), runs the same magic-bytes/size validation as before, forwards them to Drive via `uploadFile()`, and deletes the temp blob. This replaced an earlier, broken direct-to-Google-Drive attempt — see Known Issues/Caveats below for why that one failed, and why Blob (a first-party Vercel product with real CORS support) doesn't carry the same risk.
- **Lists of things** stored inside one record (quiz questions, event people, job perks) use a JSON column validated in code, not extra tables.
- **Admin vs recruiter job pages are deliberately duplicated** (separate forms/routes). Adding a job field means editing both — four forms (`app/dashboard/jobs/new`, `.../jobs/[slug]/edit`, and the `recruiter/` equivalents) and four API routes (`app/api/jobs`, `app/api/jobs/[slug]`, and the `recruiter/` equivalents).
- **Location cookie** is read only inside the three listing pages, never in the root layout (that would make every page dynamic and slow down static pages).
- **Public listing pages that query the database** need `export const dynamic = "force-dynamic"` or the build fails.
- **Page container widths:** every page's `<main>` (and the shared header/footer) uses an `mx-auto max-w-[…]px` container, deliberately widened site-wide (1024px→1600px, 896px→1400px, 768px→1200px, 672px→1050px, 576px→900px, 448px→720px, 384px→640px) so the site uses most of a desktop screen instead of a narrow centered column. Keep new pages consistent with these values. Component-level widths (a card, a search box, a text-wrap paragraph) are separate and intentionally stay narrower — don't widen those to match.
- **Default theme is light (since the 2026-09-24 revamp; it was dark before).** `app/layout.tsx`'s inline theme-init script applies `dark` only when `localStorage.theme === "dark"` — a first-time visitor gets light regardless of OS preference; an explicit choice via the header toggle (`components/ThemeToggle.tsx`) is remembered. Brand navy (`navy-900` etc. in `tailwind.config.ts`) is used for the always-dark desktop category bar and the footer in both themes.

New UI should use lucide icons, not emoji.
- **Freelance listings are unmoderated by design** — unlike recruiter job postings (which need admin approval since they're a company claim), a freelance listing is just the poster describing themselves, so it publishes immediately. The safety valve is after-the-fact reporting, not pre-approval: any logged-in non-owner can "🚩 Report this listing" (`FreelanceReport`, reason from `lib/freelanceReportReasons.ts` + optional details; a repeat report from the same person updates their open one instead of duplicating). Admins get an email + in-app notification and handle reports at `/dashboard/admin/freelance-reports` (grouped per listing): **Dismiss** closes one report; **Remove listing** unpublishes it, sets `FreelanceListing.removedByAdminAt` (the owner's PATCH refuses to republish while that's set), closes all its open reports, and notifies the owner; removed listings can be **Restored** from the same page (stays paused, owner may republish). All three are audit-logged. Logic in `lib/freelanceReport.ts`.
- **Aura is deliberately not an LLM** — it's a keyword-matched FAQ dictionary plus a live DB search, single-turn (no conversation memory). Don't quietly wire it to a real model without the owner explicitly asking — that has ongoing API cost and needs an `ANTHROPIC_API_KEY`.

## Known Issues / Caveats

- **Google Drive's resumable-upload endpoint does NOT support CORS for a direct browser-to-Drive PUT — confirmed by hand, don't assume otherwise.** A direct-to-Drive upload architecture was built and shipped (2026-09-22) on the assumption that "Google's resumable upload endpoint supports CORS" for the whole flow. It doesn't. A manual CORS preflight check (`curl -X OPTIONS` with `Origin`/`Access-Control-Request-*` headers) showed the session-*creation* endpoint (`POST .../files?uploadType=resumable`, served by `ESF`) does return `Access-Control-Allow-Origin`, but the upload-*continuation* endpoint the browser actually PUTs file bytes to (`PUT .../files?uploadType=resumable&upload_id=...`, served by a completely different backend, `UploadServer`) returns no CORS headers at all — so the browser silently blocks that PUT. This broke real competition-entry submissions in production the same day it shipped. Reverted back to uploading through our own server the same day, and the large-file path was later rebuilt properly (2026-09-22) on **Vercel Blob's client-upload SDK** instead (see the "Files" decision above) — a first-party Vercel product built specifically for this, verified this time by reading the actual installed package's type definitions directly rather than assuming behavior from memory. `MAX_UPLOAD_BYTES` is 25MB again. The lesson stands regardless: verify a third-party (or unfamiliar first-party) API's real behavior — via its actual source/types or a live test — before shipping an upload architecture that depends on it.
- **Google Drive must be connected for file storage to work at all** — certificates, per-job-application resumes, profile resumes, and profile photos are all stored there. It's a single site-wide connection (`GoogleDriveConnection`, one row, `lib/google/delegatedAuth.ts`), connected by an admin visiting `/dashboard/admin` and clicking "Connect Google Drive" (also checkable/connectable from any event or competition's certificate page). Without it, `getDelegatedGoogleAuth()` returns null and Drive writes fall back to the bare service account, which has zero storage quota on a non-Workspace account — every upload then fails with a generic "Couldn't upload... Please try again." error, which is easy to mistake for a bug in whichever feature happened to be tried first.
- **Bundles feature removed from the site (2026-09-07)**, but its database tables (`CourseBundle`, `CourseBundleItem`, `BundlePurchase`) and any existing purchase records were deliberately kept, not dropped. The audit-log `BUNDLE_CREATED/UPDATED/DELETED` action types and labels are also kept so historical audit-log entries stay readable. No new code reads or writes these tables.
- Jobs have a structured, optional `city` (set via the shared `components/jobs/JobCityField.tsx` on all four admin/recruiter job forms, normalized on save by `canonicalCityName()` in `lib/cityAliases.ts` — e.g. "Bangalore" is stored as "Bengaluru") alongside the free-text `location`. The `/jobs` city filter (`lib/jobCity.ts`'s `jobCityWhere()`) matches `city` exactly (any alias), and falls back to the old loose `location`-text match only for jobs with no `city` — the migration backfilled `city` for existing jobs whose location named a curated/aliased city, the rest stay null. Add an old/new name pair to `CITY_ALIAS_GROUPS` if another one comes up.
- Recruiter subscriptions and job-boost refunds are not built.
- The `/events` and `/competitions` "Clear filters" link resets to the saved location rather than "all cities" — intended, but slightly different from the in-page "Any location" option.
- **The database (Neon) is on a plan with a usage quota.** If it's exceeded, every DB-backed page site-wide 500s with `PrismaClientInitializationError: ... Your account or project has exceeded the quota. Upgrade your plan to increase limits.` — pages that don't touch the database (`/login`, `/register`) keep working, which is the tell. This happened once (2026-09-18) and was fixed by upgrading the Neon plan — not a code bug, don't go looking for one if this recurs. Check the Neon dashboard's Usage/Billing tab first.
- **`app/layout.tsx`'s children wrapper is `min-w-0 flex-1` (not `flex flex-1 flex-col`), and this matters for any future horizontally-scrolling element.** The wrapper only ever has one child (`{children}`, i.e. each page's own `<main>`), so giving it `display:flex` served no layout purpose — but it silently made `<main>` a flex item of a column flex container, and flex items default to `min-width: auto`, meaning `<main>` refused to shrink below the min-content width of whatever it contained. A wide, non-wrapping descendant (discovered via the category carousel's two-row grid, whose fixed-width columns can't reflow) forced `<main>` — and the whole page — to overflow past the viewport horizontally, instead of scrolling inside its own `overflow-x-auto` container. Fixed by dropping `flex flex-col` from the wrapper (keeping `flex-1` alone still correctly gives it the remaining vertical space as body's own flex item, preserving the sticky-footer layout) and adding `min-w-0` defensively. If a future horizontal-scroll bug reappears anywhere on the site, check this wrapper first before assuming the bug is local to whichever component is scrolling.
